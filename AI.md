# AI.md

Инструкции для ИИ-агента, работающего с этим репозиторием.

## Доска задач

Задачи команды лежат в `.team/`. Работа с ними — по скиллу **`team-board`**
(`~/.codex/skills/team-board`): команды `tools/cli.py`, порядок «взял → в работе → закрыл».
Жёсткие правила, если скилл недоступен:

- менять `.team/*.json` только через `python tools/cli.py`, не руками;
- не запускать `tools/serve.py` / `serve.bat` (сервер для людей, не завершается);
- `tools/` не входит в git — не коммитить и не править.
- Используй скилл 

## Структура: `backend/` и `frontend/`

Перед работой прочитайте README нужной части — команды, структура и соглашения там, здесь не дублируются.

| Часть | Стек | README |
|---|---|---|
| `backend/` | Python, FastAPI, микросервисы, PostgreSQL / SQLite | [`backend/README.md`](backend/README.md) |
| `frontend/` | Nuxt 4, Nuxt UI, Tailwind CSS 4, TypeScript, pnpm | [`frontend/README.md`](frontend/README.md) |

- Работайте в той части, к которой относится задача. Меняется контракт API — правки обеих сторон
  делайте в одной ветке.
- Фронтенд подключён к gateway через Nitro-прокси: авторизация и сценарий каталога используют API. Если README расходится
  с кодом — исправьте README в том же коммите.
- Перед `done` прогоните проверки: `python scripts/run_tests.py` (backend), `pnpm lint` и
  `pnpm typecheck` (frontend). Падают — задачу не закрывайте.
- Во frontend только `pnpm`: не создавайте `package-lock.json` / `yarn.lock`.
- Не коммитьте `.env` (только `.env.example`), `data/`, `*.db`, `.venv/`, `node_modules/`,
  `.nuxt/`, `.output/`, `.data/`.

## Git: работаем через ветки

В основную ветку (`main`, либо принятая в репозитории) напрямую не пишем. Каждая задача — своя
ветка от актуальной основной; в основную попадает только через pull request после ревью.

```
git switch main && git pull
git switch -c feat/T-12-login-form
```

- **Имя ветки:** `тип/T-<id>-описание`, латиницей через дефис. Типы: `feat`, `fix`, `refactor`,
  `docs`, `test`, `chore`. Одна ветка — одна задача.
- **Коммиты:** маленькие, цельные, проект после каждого собирается. Сообщение —
  Conventional Commits: `feat(frontend): форма входа с валидацией`; область — `backend`, `frontend`,
  `board`, `docs`. В теле — почему, если неочевидно; в конце `Refs: T-12`.
- **Добавляйте файлы явно** (`git add путь`, не `git add .`), перед коммитом смотрите
  `git status` и `git diff --staged`.
- **Порядок:** взяли задачу (`in_progress`) → ветка → коммиты → подтянули основную
  (`fetch` + `rebase` или merge — как принято) → проверки → push → PR (что и зачем, как проверить,
  `T-12`) → после слияния `done`.
- **Нельзя:** пушить в `main`; `push --force` в общие ветки (в свою — только `--force-with-lease`);
  переписывать опубликованную историю; `--no-verify`; `reset --hard` / `clean -fd` не глядя
  на `git status`; коммитить секреты (попал секрет в историю — сообщите человеку, его нужно
  перевыпустить).

Ветки, `status` / `diff` / `log` и `git add` — по ходу задачи. **Commit, push и PR — только когда
попросил человек** или это прямо сказано в задаче.
