# API-стандарт

Единый контракт для всех сервисов за `api_gateway`. Цель — фронтенд и любой новый сервис
работают по одним правилам без чтения чужого кода. Часть правил уже реализована в `common/`
(`backend/common/`) — не переизобретайте, используйте фабрику `create_app` и `AppException`.

## 1. Точка входа

Клиент (фронтенд, внешние интеграции) ходит **только** на gateway: `http://localhost:8000/api/v1/…`
(prod — за reverse proxy). Прямые обращения к портам сервисов (`:8001`, `:8002`, `:8003`…) — только
для локальной отладки конкретного сервиса (Swagger на своём порту). Gateway пересылает путь без
изменений: `/api/v1/<prefix>/…` → сервис, владеющий `<prefix>` (таблица `SERVICES` в
`api_gateway/app/core/config.py`).

## 2. Именование ресурсов

- Префикс сервиса и имена ресурсов — существительные во множественном числе, `snake_case` для
  составных слов: `/auth`, `/users`, `/items`, `/ai`. Один префикс = один сервис-владелец.
- Вложенность не глубже `/resource/{id}/sub-resource`. Если сущность используется отдельно от
  родителя — отдельный ресурс с полем-ссылкой (`task_id`), а не вечная вложенность.
- Глаголы в пути — только для действий, не выражаемых CRUD-методом (`/auth/refresh`,
  `/auth/login`). Для остального — стандартные HTTP-методы.

## 3. HTTP-методы и коды

| Метод | Смысл | Успешный код |
|---|---|---|
| `POST /resource` | создание | `201 Created` (тело — созданный объект) |
| `GET /resource` | список | `200 OK` |
| `GET /resource/{id}` | одна запись | `200 OK` |
| `PATCH /resource/{id}` | частичное обновление (`exclude_unset`) | `200 OK` |
| `DELETE /resource/{id}` | удаление | `204 No Content` |
| `POST /resource/{id}/action` | не-CRUD действие (`refresh`, `select`) | `200/201` по смыслу |

`PUT` не используем (частичные обновления через `PATCH` покрывают нужды MVP). Пример эталонной
реализации — `backend/example_service/app/api/endpoints/items.py`, копируйте паттерн для новых
ресурсов.

## 4. Формат ошибок

Один формат на весь бэкенд, гарантирован `common/exceptions.py`, менять нельзя без согласования:

```json
{ "detail": "Item not found", "code": "not_found" }
```

- `code` — стабильный машиночитаемый идентификатор, `snake_case`, на нём строится обработка на
  фронтенде (не парсите `detail`). Новый код ошибки — не изобретайте на месте, а наследуйтесь от
  `AppException` (см. `backend/ai_service/app/services/generation.py` — `ai_not_configured`,
  `ai_rate_limit`, `ai_provider_error` и т.д. — пример именования: `<домен>_<причина>`).
- Готовые базовые классы: `BadRequestError` (400), `UnauthorizedError` (401), `ForbiddenError`
  (403), `NotFoundError` (404), `ConflictError` (409). `422` FastAPI отдаёт сам при ошибке
  валидации Pydantic — формат тот же не переопределяем, оставляем стандартный FastAPI-ответ.
- Необработанное исключение → `500 { "detail": "Internal server error", "code": "internal_error" }`,
  подробности только в логах сервиса (не отдаём стектрейс клиенту).
- Ответ провайдера (OpenAI и т.п.) наружу **не пробрасывается** как есть — заворачивайте в
  `AppException` со своим `code` (см. `ai_service`): чужой формат ошибки не наш контракт, плюс
  риск утечки данных запроса.

## 5. Аутентификация

- Токены выпускает только `auth_service`: `access` (30 мин) + `refresh` (7 дней).
- Все запросы, кроме `PUBLIC_ENDPOINTS` (`api_gateway/app/core/config.py`: `auth/register`,
  `auth/login`, `auth/refresh`), — с заголовком `Authorization: Bearer <access_token>`.
- Gateway проверяет подпись и отбрасывает невалидные запросы до сервиса; сервис проверяет токен
  ещё раз сам (`token_user_dependency`) — не полагайтесь на то, что gateway уже всё проверил, если
  сервис теоретически может получить запрос в обход (внутренние вызовы сервис-сервис).
- Роль пользователя (когда появится, см. `docs/architecture.md`) — в самом JWT (claim), не отдельным
  запросом к `auth_service` на каждый вызов: это сознательный компромисс скорости ради того, что
  описан в `backend/README.md`.

## 6. Пагинация и списки

Стандарт (пример — `GET /items`): query-параметры `limit` (по умолчанию 50, максимум 200) и
`offset` (по умолчанию 0). Пока список отдаётся как плоский JSON-массив — это осознанное
упрощение MVP, **не подходит** для каталога, которому нужна сортировка по рейтингу с пагинацией
на фронте. Для таких ресурсов (в первую очередь — каталог задач) используйте обёртку сразу:

```json
{ "items": [...], "total": 128, "limit": 50, "offset": 0 }
```

Не мигрируйте существующие простые списки (`/items`) без необходимости — новый формат вводите
для новых ресурсов, где пагинация действительно нужна клиенту.

## 7. Версионирование

Префикс `/api/v1` — общий для всех сервисов, меняется целиком, не по сервисам отдельно.
Ломающее изменение контракта (переименование/удаление поля, смена типа, смена кода ошибки) —
через новую версию префикса **только если** аддитивное решение невозможно; в остальном действует
принцип «только аддитивно»: новые поля — опциональны, старые клиенты не ломаются. Любое изменение
схемы (`*/app/schemas/`) — отдельный коммит с пояснением, фронтенд обновляется в том же PR или
сразу следующим (см. `AI.md`).

## 8. Health и наблюдаемость

- `/healthz` — процесс жив, без проверки зависимостей (liveness).
- `/health` — читает зависимости (БД и т.д.), `503` при сбое (readiness); у gateway агрегирует
  `/health` всех сервисов из `SERVICES`.
- Каждый запрос получает `X-Request-ID` (или использует переданный) — попадает в лог одной
  структурой (`common/middleware.py`, `common/logger.py`). При разборе бага между сервисами ищите
  по этому id, а не по времени.

## 9. Rate limiting

Только на gateway (`RATE_LIMIT_PER_MINUTE`/`_HOUR`) — сервисы за ним лимит не ставят, иначе
задушат сами себя (внутри сети все запросы приходят с IP gateway). Не добавляйте лимитер внутрь
нового сервиса.

## 10. Новый сервис — обязательный чек-лист

Полная процедура — «Добавление сервиса» в `backend/README.md`. Коротко, что нельзя забыть:

1. Скопировать `example_service/` как основу (уже соответствует слоям из `architecture.md`).
2. Зарегистрировать в `api_gateway/app/core/config.py`: `Settings` + `SERVICES`.
3. `docker-compose*.yml`, `.env.example`, `postgres-init/`.
4. Добавить в `scripts/run_tests.py` и `scripts/run_local.py` — иначе `start.bat` и CI сервис не
   увидят.
5. Обновить `docs/architecture.md` (карта доменов) и, если меняется контракт, этот документ.

## 11. Чего в MVP сознательно нет

Идемпотентность через `Idempotency-Key`, кэширование ответов, GraphQL/gRPC между сервисами,
единый агрегированный Swagger на gateway. Не добавляйте, пока не появится конкретная причина —
см. принцип «не проектируем под гипотетическое будущее» в стиле работы репозитория.
