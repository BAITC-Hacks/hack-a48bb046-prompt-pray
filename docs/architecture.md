# Архитектура

Как устроен один сервис изнутри (чистая архитектура, коротко) и как доменные сущности из
[`AGENTS.md`](../AGENTS.md) («AI Sana») ложатся на сервисы. Правила контракта между сервисами —
в [`api-standards.md`](api-standards.md).

## Слои внутри сервиса

```
api/          роуты, зависимости (auth, сессия БД), валидация входа/выхода — HTTP и ничего больше
  ↓
services/     бизнес-логика, транзакции (commit), вызовы других сервисов
  ↓
repositories/ запросы к БД — никакого FastAPI, никакой бизнес-логики
  ↓
models/       SQLAlchemy ORM
schemas/      Pydantic — контракт запроса/ответа, отдельно от models/
```

Зависимость — только сверху вниз. `repositories/` не знает про `api/`, `models/` не знает про
`schemas/`. Эталон — `backend/example_service/`, копируйте его при создании нового сервиса, а не
пишите слои с нуля. `schemas/` — источник истины контракта: при синхронизации с фронтендом
сверяйтесь с ними, не с реализацией эндпоинта.

`common/` (`backend/common/`) — не слой одного сервиса, а инфраструктура, одинаковая для всех:
`create_app` (middleware, health, обработчики ошибок), `auth.py` (JWT), `db.py` (async
SQLAlchemy), `exceptions.py`. Новую сквозную возможность (логирование, безопасность) добавляйте
туда, а не дублируйте в сервисе.

## Карта сервисов

```
Клиент ──► api_gateway :8000 ──► auth_service      :8001 ──► auth_db
           (JWT, CORS,           example_service   :8002 ──► example_db   (шаблон, не продукт)
            rate limit,          ai_service         :8003 ──► (без БД, только OpenAI)
            маршрутизация)       catalog_service    :8004 ──► catalog_db
```

- **`auth_service`** — пользователи, токены, `/users/me`. Владеет тем, *кто* обращается к системе.
- **`ai_service`** — тонкая обёртка над OpenAI Responses API. Намеренно не знает о домене
  («задача», «карточка», «рейтинг») — принимает `prompt`/`instructions`, отдаёт текст. Это
  осознанное разделение: доменная логика (какие вопросы задавать, как собрать карточку) не должна
  жить рядом с провайдер-специфичным кодом, иначе смену модели/провайдера придётся тянуть через
  бизнес-логику.
- **`example_service`** — не продуктовый сервис, шаблон слоёв для копирования (см. `items`).
- **`catalog_service`** (доменный слой T-3; каркас и API развиваются в T-2/T-4/T-6) — владеет доменом «AI Sana» целиком: `TaskDraft`,
  `ClarifyingQuestion`, `TaskCard`, `RatingBreakdown`, `CatalogEntry`, `Proposal`,
  `SelectionDecision`. Один сервис на весь домен — сущности сильно связаны сценарием (черновик →
  карточка → рейтинг → каталог → отклик → выбор) и меняются вместе; дробить на отдельные сервисы
  сейчас — преждевременная сложность без причины (лишние сетевые вызовы и согласование транзакций
  между «карточкой» и «рейтингом», которые физически один агрегат).

## Доменные сущности → поля/сервис

| Сущность (`AGENTS.md`) | Владелец | Примечание |
|---|---|---|
| `TaskDraft` | `catalog_service` | свободный текст бизнеса, ссылка на `business_id` (id из `auth_service`, без FK между БД) |
| `ClarifyingQuestion` | `catalog_service` | генерируется через вызов `ai_service` (`POST /ai/generate`), минимум 3 |
| `TaskCard` | `catalog_service` | собирается из ответов, редактируема, требует подтверждения бизнесом |
| `RatingBreakdown` | `catalog_service` | пересчитывается при каждом изменении карточки — считать в `services/`, не хранить производные без пересчёта при обновлении |
| `CatalogEntry` | `catalog_service` | подтверждённая `TaskCard`; публичный `GET`, без аутентификации на чтение (решить отдельно — см. ниже) или с ней, если каталог не публичен для анонимов |
| `Proposal` | `catalog_service` | отклик команды, ссылка на `task_id` + `team_id`/`user_id` |
| `SelectionDecision` | `catalog_service` | ручное решение бизнеса, не автоматическое сопоставление — **никогда** не считать это подбором очереди |

Межсервисные ссылки (`business_id`, `team_id` → `auth_service`) — по `id`, без FK на чужую БД
(правило «у каждого сервиса своя база», `backend/README.md`). Проверка существования пользователя
— по данным из токена (`common/auth.py`), не отдельным HTTP-вызовом к `auth_service` на каждый
запрос (см. `api-standards.md`, п. 5).

## Роли пользователей

`auth_service` хранит роль `business|student` и возвращает её в `/users/me` и JWT.
Регистрация без роли и существующие пользователи получают `student`.
Бизнес создаёт и подтверждает свои карточки, просматривает отклики и вручную выбирает команды;
студент отправляет отклик. Старый access-токен без роли требует refresh/login для доменных действий.
Публичны чтение каталога и опубликованной карточки; черновики, изменения и решения требуют
роли и проверки владельца внутри `catalog_service`.
