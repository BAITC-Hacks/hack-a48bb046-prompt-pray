## T-1 — роли пользователей

Добавил разделение пользователей на две роли:

| Значение | Назначение |
|---|---|
| `business` | Представитель бизнеса, который будет создавать и подтверждать задачи, выбирать команды |
| `student` | Студент, который будет просматривать каталог и отправлять предложения |

Роль сохраняется в модели `User`, принимается при регистрации, возвращается
в `GET /api/v1/users/me` и включается в access-токен JWT. Общий обработчик
`common.auth` передаёт роль в `TokenUser`, чтобы другие сервисы могли проверять права.
Сами проверки прав на действия с задачами относятся к следующим доменным задачам.

Для совместимости с прежними клиентами регистрация без поля `role` использует
`business` в моей первоначальной реализации. После командной интеграции значение
по умолчанию изменено на `student`; для бизнес-аккаунта роль нужно передать явно.
Неизвестное значение, например `admin`, отклоняется с кодом `422`.
Поле `is_admin` остаётся отдельным признаком и не заменяется ролью.

Пример запроса `POST /api/v1/auth/register`:

```json
{
  "email": "student-check@example.com",
  "username": "student_check",
  "password": "Check-pass-123",
  "role": "student"
}
```

После входа access-токен содержит `"role": "student"`, а `/users/me` возвращает
это поле вместе с остальными данными пользователя. Пароль и его хеш в ответ не входят.

Изменённые файлы:

- `backend/auth_service/app/models/user.py` — хранение роли.
- `backend/auth_service/app/schemas/user.py` — контракт регистрации и ответа.
- `backend/auth_service/app/services/auth.py` — сохранение роли и выдача JWT.
- `backend/common/auth.py` — общий тип роли и чтение claim из токена.
- `backend/auth_service/tests/test_auth_flow.py` — проверки обеих ролей и неверного значения.

**Результат проверки:** 8 тестов `auth_service` прошли.

В моей первоначальной реализации T-1 отдельной миграции существующей таблицы
`users` не было. `create_all` создаёт новую таблицу, но не добавляет колонку в уже
существующую. Для старой базы нужна миграция; она появилась позднее в ветке
`feat/ai-content-service` другого участника.

## T-2 — каркас сервиса каталога

На основе структуры `example_service` создал `backend/catalog_service`:

```text
catalog_service/
├── app/
│   ├── api/            маршруты и зависимости авторизации
│   ├── core/           настройки сервиса
│   ├── db/             подключение к своей базе данных
│   ├── models/         место для доменных моделей
│   ├── repositories/   место для запросов к базе
│   ├── schemas/        схемы запросов и ответов
│   ├── services/       место для бизнес-логики
│   └── main.py         приложение и его запуск
├── tests/
├── Dockerfile
├── pytest.ini
└── requirements.txt
```

Подключил сервис к gateway через `CATALOG_SERVICE_URL` и префикс `catalog`.
Добавил его в `run_local.py`, `run_tests.py`, зависимости локального запуска,
оба Compose-файла, `.env.example` и скрипт инициализации PostgreSQL.
Обновил архитектурную документацию.

При локальном запуске каталог использует порт `8004` и SQLite-файл
`backend/data/catalog_service.db`. Для PostgreSQL предусмотрены отдельные
`CATALOG_DB_NAME`, `CATALOG_DB_USER` и `CATALOG_DB_PASSWORD`.

| Маршрут | Назначение |
|---|---|
| `GET http://localhost:8004/health` | Проверяет готовность каталога и доступность его БД |
| `GET http://localhost:8004/healthz` | Проверяет, что процесс сервиса работает |

бизнес-задач, публикация, рейтинг и отклики не реализовывались.

- В Compose добавлена отсутствовавшая запись `ai_service`, который gateway уже
  учитывал в общей проверке здоровья.
- В `start.bat` добавлен запасной запуск через Python из `.venv`, если `py` и

## T-17 — язык AI-уточнений

Добавил `TaskDraft.locale`: `ru`, `kk` или `en`. Старые запросы без поля продолжают
работать с `ru`; неизвестный язык и явный `null` возвращают `422`. Язык сохраняется
в БД и возвращается при создании, чтении одного черновика и списка своих черновиков.

Пример `POST /api/v1/catalog/drafts`:

```json
{
  "description": "Нужно подготовить отчёт по продажам",
  "locale": "kk"
}
```

Генерация берёт язык из сохранённого черновика и передаёт в AI инструкции писать
вопросы на русском, казахском или английском. Требования задать минимум три вопроса
по недостающим данным и не выдумывать факты сохранены. Описание, уже сохранённые
вопросы и ответы автоматически не переводятся. Повтор генерации возвращает
существующие вопросы, а ошибка AI не удаляет черновик.

В форме создания добавил выбор языка вопросов. После сохранения язык фиксируется;
при повторном открытии загружаются сохранённые язык и ответы. Повторная загрузка
вопросов не затирает несохранённый текст в текущей форме.

Для старых баз добавил идемпотентный upgrade `migrate_draft_locale`: новая колонка
получает `ru`, `NOT NULL` и ограничение допустимых значений. Текущие тексты и связи
сохраняются. Код — `backend/catalog_service/app/db/migrations.py`.

**Осталось до полного закрытия:** подключить начальный язык формы к общему
переключателю T-19 и проверить смену языка UI без потери ввода. После появления
T-15 перенести upgrade в версионируемую миграцию и проверить её на PostgreSQL.
Общий переключатель интерфейса в рамках T-17 не реализован.

## T-18 — защита карточки от потери изменений

Добавил `TaskCard.version`, начиная с `1`. Сохранение, подтверждение и публикация
требуют положительный целочисленный `expected_version`, полученный при чтении
карточки. Каждая успешная операция увеличивает версию на один.

Пример PATCH `/api/v1/catalog/tasks/{id}`:

```json
{
  "expected_version": 3,
  "data": "Добавлен пример исходных данных"
}
```

Проверка выполняется одним условным UPDATE в БД. Если два запроса используют
одинаковую версию, успешно проходит только один. Второй получает `409` с кодом
`catalog_version_conflict`, без перезаписи первого результата. Проверка действует
также при подтверждении и публикации: устаревшую карточку нельзя подтвердить или
опубликовать после чужого изменения.

Содержимое, рейтинг, снятие подтверждения/публикации и увеличение версии выполняются
в одной транзакции. При ошибке откатываются все эти изменения, включая версию.

Фронтенд передаёт версию последнего успешного ответа на каждом шаге. При конфликте
он сохраняет введённый текст и предлагает загрузить актуальную карточку. После
загрузки прежний ввод остаётся отдельной копией для сравнения; пользователь может
явно вернуть его в форму и проверить перед сохранением. Автоматической перезаписи
или повтора с новой версией нет. Копия хранится в памяти страницы и не переживает
полную перезагрузку или уход со страницы.

Для существующих карточек добавил upgrade `migrate_card_version`: версия `1`,
`NOT NULL` и проверка `version >= 1`, без сброса данных. Код —
`backend/catalog_service/app/db/card_version_migration.py`.

**Совместимость API:** чтение получает дополнительное поле `version`, но старые
запросы записи без `expected_version` теперь возвращают `422`. Подтверждение принимает
`{confirmed: true, expected_version}`, публикация — `{expected_version}`. После
публикации следующую версию нужно брать из `task.version` ответа. Backend и frontend
следует обновлять совместно; обновлены также smoke-скрипт и интеграционные тесты.

**Осталось до полного закрытия:** после T-15 перенести upgrade в версионируемую
миграцию и проверить на PostgreSQL, затем провести командное ревью и слияние.
Backend и клиент T-18 подготовлены совместно в `codex/T-18-card-version`.
